## 1. Production is currently broken — and I caused it

**Root cause: the live database has been migrated ahead of the deployed
code.** Today's session ran three schema migrations directly against the
Neon database at `ep-lingering-leaf-a56njnl5.us-east-2.aws.neon.tech/neondb`
— the same `DATABASE_URL` configured in this project's `.env`. Before
running them, I explicitly asked whether that database was a personal/dev
branch or something shared/production, and was told personal/dev. Given
what's now visible at `bribar-logistics.vercel.app`, **that database is
what backs the live Vercel deployment** — so the migrations landed on
production, while the *code* deployed on Vercel is still the old code from
commit `df6d9f3` (the local repo is 2 commits ahead of `origin/master`;
neither commit has been pushed).

Old deployed code + migrated database = every code path that touches the
columns I changed now throws, because the column it expects is gone or a
new required column has no value to send.

### Confirmed broken paths

**`refuellings.payment_method_id` was dropped** (migration
`20260916213318_refuelling_drop_payment_method`), but the deployed code
(`df6d9f3`) still has it baked into `REFUELLING_INCLUDE`:

```ts
// src/modules/refuelling/repository/refuelling.repository.ts (deployed version)
const REFUELLING_INCLUDE = {
  vehicle: { ... }, driver: { ... }, fuelType: { ... },
  gasStation: { ... },
  paymentMethod: { select: { id: true, name: true } },   // <- column is gone
} satisfies Prisma.RefuellingInclude;
```

Any query using this include issues a JOIN against a column that no longer
exists → Postgres error → surfaces to the browser as the generic masked
"Server Components render" error (React minified #441 — Next.js hides the
real message in production and only shows a digest). This breaks:

- The refuellings list, detail and edit pages.
- **Every lookup-item edit page, for every kind** — including the
  `GAS_STATION` one you hit. `lookupRepository.countDependents` in the
  deployed code unconditionally runs
  `client.refuelling.count({ where: { paymentMethodId: id } })` on *every*
  call, regardless of which kind's page you're on:

  ```ts
  // src/modules/lookup/repository/lookup.repository.ts (deployed version)
  const [asFuelType, asGasStation, asRefuellingPaymentMethod, ...] = await Promise.all([
    client.refuelling.count({ where: { fuelTypeId: id } }),
    client.refuelling.count({ where: { gasStationId: id } }),
    client.refuelling.count({ where: { paymentMethodId: id } }),  // <- throws
    ...
  ]);
  ```

  This is exactly the query behind
  `/admin/lists/GAS_STATION/01a08aee-5247-70b5-8b4e-a8ae933a894a`.

**`received_invoices.concept` was added as required** (migration
`20260916223831_received_invoices_add_concept`), but the deployed code's
schema has no `concept` field at all. Creating a new received invoice
through the *old* deployed UI now fails with a NOT NULL violation. (Reading
existing invoices still works — a SELECT that doesn't ask for the column is
fine.)

**`end_clients` / `routes.end_client_id`** — additive only, nothing in the
deployed code references it, so this one migration alone is harmless to old
code.

## 2. What the change request still needs

Matches the client-facing summary (`docs/RESUMEN_CAMBIOS_2026-09-17.txt`),
with the technical detail behind each item.

### "Empresa" scope in the Dashboard vehicle filter
Not started. `analyticsService.overview`/`vehicleStats` and the filter
schema (`src/modules/analytics/schemas/analytics.schema.ts`) only support
"all vehicles" or one specific vehicle — there's no third `companyOnly`
branch, and the `<select>` on `/admin/analytics` has no sentinel option for
it. Needs: a scope where services/refuellings/daily-km are excluded
entirely and only vehicle-less (`vehicleId: null`) received invoices and
fleet-wide personnel cost count — i.e. the existing "Empresa (sin vehículo
asociado)" concept `ReceivedInvoice` already has, surfaced as a real filter
option.

### Análisis: daily-summary and per-service tables
Not built as standalone tables. What exists instead: the service detail
page (`/admin/services/[id]`) now shows estimated fuel cost and gross
margin for *that one* service, and `analyticsService.vehicleStats` gives a
per-vehicle (not per-day, not per-service) fuel/consumption breakdown. The
client asked for a day-by-day table (date, revenue, actual km, estimated
fuel cost) and a service-by-service table with the same columns, both on
the Análisis page itself. Neither exists as a queryable table yet.

### Personnel: drop the leftover columns
Not done. `PersonnelCost` still has `overtimeCents`, `allowancesCents`,
`otherCents` (schema, `personnel-cost.schema.ts`, the admin form, the list
column). Per the client's instruction, these should go, and `totalCents`
should become a directly-entered field instead of the server-computed sum
of the four. "Tributa" (column K in the source sheet) was never added and
doesn't need to be. This needs its own migration —
`DROP CONSTRAINT personnel_costs_total_formula` and
`personnel_costs_amounts_non_negative` before dropping the columns, a
narrower non-negativity check after.

### Investments: month-by-month per-vehicle profit table
Not started. `/admin/investments` has the Total Inversión table and the
all-time cumulative Recuperación table; it's missing the literal ask —
Vehículo × Mes → Facturación / Combustible / Gastos de explotación /
Resultado de explotación, broken out monthly, not fleet-wide-per-month
(the existing dashboard chart) or all-time-per-vehicle (the existing
Recuperación table). `analyticsService` needs a `monthlyMarginByVehicle`
query grouped by `(vehicleId, year, month)`; nothing computes this today.

### Maintenance alert thresholds
Deliberately left provisional per your earlier answer — this one is
blocked on you, not on engineering: the current URGENT/UPCOMING bands
(500 km / 14 days, 2000 km / 30 days) in
`src/modules/maintenance/domain/maintenance-urgency.ts` are placeholders.
Needs the real per-maintenance-type thresholds from you before this can be
finalized.
